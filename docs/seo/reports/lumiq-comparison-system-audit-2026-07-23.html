Executive Summary

The single most important finding of this audit was not requested by name in the brief, but it answers the brief's real underlying question.

3 of the 4 live comparisons are broken: they show only one tool, not two

Critical

chatgpt-vs-claude, midjourney-vs-dalle3, and github-copilot-vs-cursor each have exactly 1 ComparisonSide row instead of 2. Root cause, reproduced directly: scripts/seed-comparisons.ts hardcodes tool slugs (claude-anthropic, dall-e-3, cursor) that do not match the actual live AITool.slug values (claude, dalle-3, cursor-ai-code-editor). The script's own lookup (bySlug[s.slug]) silently failed, filtered the missing side out via .filter(Boolean), and inserted the comparison anyway because the script's guard is if (sidesData.length < 1) — not < 2. This is the opposite of the real admin API's rule (app/api/admin/comparisons/create/route.ts requires sides.length >= 2), meaning the seed path and the "real" creation path enforce different rules and one of them produced bad data that has been live in production undetected.

DB: ComparisonSide count per Comparison, live query Verified: AITool.findUnique for each hardcoded slug — 3/3 return null scripts/seed-comparisons.ts:165

This finding reframes the whole audit. The system's architecture is not the primary obstacle to scaling — it is reasonably sound (N-way comparisons are already supported, the listing query has no N+1 risk, sitemap/robots/schema are correctly wired). The primary obstacle is that the only path from "idea" to "published comparison" that has ever actually been used is a one-off script with no safety net, because the real admin UI has no working edit page and a duplicate, unvalidated API route exists alongside the validated one. Scaling to 100+ comparisons on this workflow would reproduce this exact class of silent failure at higher volume.

Separately, the schema's ComparisonSide.toolId is a hard foreign key to AITool specifically — not a generic/polymorphic reference. This means the system cannot compare a crypto exchange, a sports team, or a health app today under any configuration; every future domain requires new tables. This is expected for a single-purpose feature and is not itself a defect, but it directly answers the brief's cross-domain question: reuse requires a schema extension, not just content entry.

Answers to the 8 required questions

1. Can the model support richer comparisons without a migration?

Partially. Scoring, pros/cons, verdict, and N-way sides work today. FAQ, citations, affiliate links, sponsor labels, and update-history all require new columns — none exist.

2. Which future blocks can already be stored?

Per-side score, strengths/weaknesses, "best for," a freeform verdict, and a freeform criteria list.

3. Which blocks cannot currently be stored?

FAQ (Review and AITool both have faq Json?; Comparison does not), sources/citations (Review has sources Json; Comparison does not), affiliate URL, sponsor disclosure, methodology/benchmark data, last-reviewed date distinct from updatedAt, author attribution (Review has authorSlug; Comparison has no author field at all).

4. Are any fields overloaded or semantically unclear?

criteria: Json? is used as a flat array of criterion labels in all 4 live records (["جودة الإجابات", "الأمان والصدق", ...]) with no per-tool scoring against each criterion — meaning the criteria list is currently decorative (rendered as chips) and not connected to the scoring system at all. This is a real semantic gap: a reader sees 5 "comparison criteria" and 2 score rings, with no visible link between them.

5. Can more than two items be compared?

Yes, already. ComparisonSide[] is an unbounded relation, the create form's addSide() has no upper limit, and the detail page's rendering (comparison.sides.map(...), grid layout) does not assume exactly 2. This is confirmed working architecture, not a gap.

6. Can the model support AI, Crypto, Sports, Health, Finance comparisons?

No, not as-is. ComparisonSide.toolId is a required, non-nullable foreign key to AITool specifically. A crypto exchange or sports team has no AITool row and cannot legally satisfy this constraint.

7. Would adding another domain pollute the current schema?

Forcing a Crypto/Sports/Health entity into the AITool table (e.g., adding a domain column to AITool and reusing it for a Binance or Bybit "tool") would pollute it — AITool has AI-specific fields (arabicSupport, hasApi, toolCategory drawn from a fixed AI-tool taxonomy) that don't map to a crypto exchange or a sports team.

8. Hidden scalability risks at 100–500?

None found at the schema level (proper indexes, proper unique constraints). The risk at that scale is entirely at the query/UI layer (see §5), not the data model.

Inspection of the 4 live comparisons

Structural consistency: yes for schema shape, no for actual completeness

All 4 use the same fields (title, summaryAr, verdict, criteria as a 5-item array, published=true). But 3 of 4 have only 1 side where 2 were intended — so while the shape is consistent, the content is not.

Scoring consistency

All scores fall in a narrow 78–92 band with no documented scale or methodology — no criterion-by-criterion breakdown exists despite 5 named criteria per comparison, so the single overall score cannot be traced back to how it was derived. This is a real bias-prevention gap (see §8).

Verdicts: evidence-based? No — they are editorial opinion with no citation

All 4 verdicts are well-written, plausible, single-paragraph judgments (109–131 characters) with zero footnotes or source references, consistent with the absence of any citation field.

Pricing currency: cannot be verified as "current" by the system itself

createdAt === updatedAt for all 4 records exactly — none has been touched since May 28, 2026, roughly 8 weeks before this audit. There is no mechanism that would surface "this comparison hasn't been reviewed in N weeks."

Missing required fields

3 of 4 comparisons are missing an entire second ComparisonSide — not a partial field, an entire missing entity relation.

Frontend and UI audit

Listing page — app/(main)/compare/page.tsx

Server component, force-dynamic. Fetches up to 24 published comparisons via a single findMany with nested include (no N+1 risk). Renders a responsive 2-column card grid (RTL-correct, dir="rtl" throughout), tool avatars with a "VS" badge between sides, a score progress bar per side, and an empty-state ("لا توجد مقارنات بعد") for the zero-comparisons case. No pagination — take: 24 is a hard cap with no page/skip handling found anywhere in the file.

Detail page — app/(main)/compare/[slug]/page.tsx

Server component, force-dynamic, notFound() on missing/unpublished slug. Renders a hero, a "VS" row with circular ScoreRing components (hand-rolled SVG, not a shared component), criteria chips, per-side strengths/weaknesses cards (green/red), a verdict box, and 3 "other comparisons" you might like. All local subcomponents (ToolAvatar, ToolLogo, ScoreRing) are defined inline in the page file rather than imported from components/ — they are not reusable elsewhere without copy-pasting.

08

Revenue readiness audit

1. Can affiliate links be added today without code?

No. There is no field to store an affiliate URL distinct from AITool.website, and no code path swaps in a tracked URL — this requires at minimum a new nullable column and a template change to use it.

2. Can they be tracked?

No dedicated click-tracking exists for comparison CTAs specifically. ToolEvent (type: view/like/click) exists as a model and could be extended, but nothing wires a comparison-page outbound click into it today.

3. Can sponsored placements be clearly disclosed?

No — no sponsor field, no disclosure UI block exists anywhere in the comparison rendering.

4. Can comparison performance be measured separately?

Partially — Comparison.viewCount exists but reads 0 on all 4 live records, meaning either it was never wired to increment, or genuinely has zero traffic. Given other pages (reviews, tools) correctly increment their own viewCount fields elsewhere in the codebase, this is worth flagging as likely unwired for comparisons specifically — not confirmed either way in this audit (see §14 Uncertainties).

5. Smallest safe revenue improvement?

Add a nullable affiliateUrl field to AITool (it already has website) and conditionally use it in the existing outbound CTA wherever it's set — purely additive, zero migration risk to existing rows, fully backward compatible.

6. What must exist before affiliate rollout?

The affiliate-URL field itself, a click-tracking wire-up (reusing the existing ToolEvent model), and — separately, an editorial/legal matter outside this audit's code scope — a disclosure UI element, since undisclosed affiliate links on a comparison page carry real regulatory/trust risk.

12

Final verdict

Verdict

OPTION B — EVOLVE INCREMENTALLY

The foundation is usable — the data model, rendering shell, and SEO wiring are all sound enough to keep — but several concrete additions are required before scaling, and one active data-integrity bug must be fixed before writing any more content on top of the current workflow.

Confidence: 82%

Exact evidence for this verdict

  • The core shell (schema, listing/detail pages, sitemap, JSON-LD) is reusable and already handles the brief's hardest architectural question (N-way comparisons) correctly — this rules out a full rebuild of that layer.
  • The editorial workflow has a missing edit page, two inconsistent create endpoints, and a proven bug that has silently corrupted 75% of live records — this rules out "keep as-is with no changes."
  • Cross-domain reuse requires a real schema change (the hard AITool FK) — not a config change — which is exactly what "evolve incrementally" (add domain extensions to a kept core) describes, rather than either extreme.

Why OPTION A (Keep and improve) was rejected

"Keep and improve" implies the current workflow can be trusted as-is with cosmetic polish. It cannot: 3 of 4 live comparisons are broken due to a workflow-level bug (silent slug mismatch, no enforcement), and the only path to fixing a published comparison today is direct database access. Improving copy or styling without first fixing the create/edit workflow would let the same class of bug recur at 20 or 100 comparisons.

Why OPTION C (Rebuild) was rejected

The brief instructs not to recommend rebuild unless evidence clearly requires it, and the evidence does not: the schema already supports N-way comparisons, scoring, drafts, and the rendering layer is force-dynamic (zero build-time cost growth) with no N+1 query risk found at any tested scale. None of the defects found (missing edit page, duplicate create endpoints, missing fields, hard FK) require discarding the existing model — they require additive migrations and new routes/pages layered on top of what exists. A rebuild would throw away genuinely correct, reusable work to fix problems that are additive by nature.
