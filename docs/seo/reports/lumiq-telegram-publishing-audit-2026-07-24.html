Executive Summary

The Telegram pipeline works, runs once daily, and is built on a genuinely reusable multi-platform provider abstraction. But the parts specific to Telegram itself — caption formatting, retry safety, and drafting — carry real, previously-undetected defects.

The Telegram message is likely rendering broken formatting today

Critical

The caption template wraps the title in Markdown asterisks (*{title}*), but the API call sets parse_mode: "HTML" — Telegram's HTML parser does not interpret *text* as bold. Every Telegram post since this code shipped has likely shown literal asterisk characters around the title instead of bold text.

A crash between "Telegram accepts the message" and "DB marks it sent" causes a real duplicate post

Critical

The send call and the status update are two independent operations with no transaction. If the process is interrupted in between — a timeout, a cold-start kill — the post stays approved and gets sent again on the next cron run. There is no idempotency key and no unique constraint guarding against it (unlike SyndicationPost, which does have one).

A failed send has no path back to success

Critical

failed is a terminal status. Nothing re-queues it, no admin action exists to retry it, and there's no distinction between a permanent failure (bad credentials) and a transient one (rate limit, network blip) — both land in the same dead end.

Beyond these three, the system has one Telegram-posting opportunity per day (09:30 UTC, 30 minutes after articles publish), sends text-only messages relying entirely on Telegram's own link-preview unfurling for the image, uses fully static hashtags never derived from the article's actual tags, and only supports the Review content type — Tools, Comparisons, and Prompts have no Telegram path at all. The underlying provider abstraction (5 platforms already registered: Telegram, Twitter, Facebook, Instagram, TikTok) is a genuine strength that would support new channels cleanly — the caption-authoring layer sitting on top of it is the part that isn't ready.

01

Current publishing architecture

Two separate crons, thirty minutes apart, connected only by a database row.

Stage 1 — Drafting

Runs inside the article auto-publish cron, not as a Telegram-specific job.

/api/cron/publish-review (09:00 UTC) → approveReview() → for every enabled SocialAccount, builds a caption and inserts a SocialPost row with status: "approved" already set — auto-approved, no human review step.

Stage 2 — Sending

A separate cron, 30 minutes later, that actually calls the Telegram Bot API.

/api/cron/social-queue (09:30 UTC) → pulls up to 10 approved posts → builds the UTM-tagged URL → calls the matching provider's send() → flips status to sent or failed.

There is no queue, worker pool, or scheduler beyond Vercel's cron primitive — SocialPost.status in Postgres is the queue. Credentials are entirely database-driven (SocialAccount.credentials, a JSON-stringified blob), not environment variables — no TELEGRAM_BOT_TOKEN exists anywhere in the codebase.

Two competing caption-building implementations exist

Medium

The one actually used, buildCaption() in lib/review-queue.ts, is a plain hardcoded if/else. A second, more sophisticated GPT-4o-mini-based generator (lib/social/generate.ts, using per-platform PLATFORM_HINTS for style/length/hashtag count) is fully implemented but never called from any reachable path — dead code that the project's own documentation incorrectly describes as active.

function buildCaption(platform: string, title: string, summary: string, url: string): string { if (platform === "telegram") { return `📰 *${title}*\n\n${summary}\n\n🔗 ${url}`; // Markdown asterisks } ... } // telegram.ts: body: JSON.stringify({ chat_id, text, parse_mode: "HTML", ... }) // HTML parse mode — mismatch

Content-type coverage: the entire pipeline only handles the Review model. SocialPost.reviewId is a hard, non-nullable foreign key — there is no equivalent drafting path for AITool, Comparison, or Prompt content. Only one template exists, and it is Review-only.

Error handling

Failure modeWhat actually happens
Telegram API rejects the request!res.ok throws a plain Error with the response body text; caught by the per-post try/catch, post marked failed with the raw error message stored in errorMsg. No retry.
Rate limit (HTTP 429)Treated identically to any other failure — no read of Telegram's retry_after field, no backoff. Marked failed permanently on the first 429.
Network failurefetch() rejection propagates to the same catch block — same terminal failed outcome, no distinction from an application-level error.
Bot blocked / chat not foundTelegram returns a non-2xx response, handled the same as any other API error — no special detection or account-disable logic.
Image unavailableNot applicable to failure handling — the code never explicitly fetches/uploads an image for Telegram in the first place (see §04); an unreachable OG image would just mean Telegram's own unfurler shows no preview, silently, with no error surfaced anywhere in this pipeline.
One post's failure blocking othersDoes not happen — the per-post try/catch means one failure doesn't stop the batch of up to 10 from continuing.
Silent swallowingThe social-drafting block itself (Stage 1) is wrapped in a bare catch {} with no logging — if drafting fails, nothing is recorded anywhere, and the article publish succeeds normally with zero visibility into the miss.
07

Current strengths & weaknesses

✓ Strengths

  • Real provider abstraction — SocialProvider interface + registry already supports 5 platforms with a uniform contract
  • Untyped string platform columns mean adding a provider needs no schema migration
  • Publish itself is never blocked by social-drafting failures — all side effects (embedding, memory extraction, WordPress syndication, social drafting) are deliberately best-effort
  • Auto-approval removes a manual bottleneck that previously caused posts to get stuck (a real, since-fixed bug — evidence in orphaned diagnostic scripts)
  • Batch processing caps at 10 posts per run, bounding worst-case cron duration

✕ Weaknesses

  • Caption authoring is not abstracted — hardcoded if/else per platform, unlike the clean sending layer
  • No retry, no dead-letter recovery, no rate-limit awareness
  • No transactional safety around the one place a duplicate-send is actually possible
  • Static hashtags ignore real tag data already sitting on the Review model
  • Text-only messages depend entirely on Telegram's own unreliable link-unfurling for imagery
  • Single content type supported (Review) despite Tools/Comparisons/Prompts existing as first-class published content

09

Production risks

Broken bold formatting has likely shipped in every Telegram post since this code went live

Critical

Not a hypothetical — this is a straightforward parse_mode/syntax mismatch that would visibly show literal asterisk characters around the title in every message actually sent to the channel.

A cron timeout or cold-start crash mid-send produces a real duplicate post to the public channel

Critical

With maxDuration = 60 and sequential (non-parallel) processing of up to 10 posts, a slow Telegram response increases the odds of hitting this exact window. There is no way to detect or prevent it after the fact — no unique constraint, no idempotency key.

The cron auth check fails open

Critical

verifyCronSecret() returns true (authorized) if CRON_SECRET is ever unset in the environment — an unset env var silently disables the auth check entirely rather than blocking the route.

A single Telegram failure is invisible beyond the admin panel

High

No alerting, no external monitoring hook — a failed post sits as a row with status: "failed" that nobody is notified about unless someone opens the admin UI.

Silent failure in the drafting step

High

The bare catch {} around social-post drafting in approveReview() means a drafting failure leaves zero trace — not even a log line — while the article itself publishes successfully, creating an invisible gap between "article live" and "social post exists at all."

10

Scalability assessment — can this support new channels?

Yes for sending, no for authoring — the architecture is half-ready.

What would extend cleanly without redesign: the SocialProvider interface and getProvider() registry are already platform-agnostic. Adding Discord, Bluesky, or WhatsApp Channels means writing one new provider file matching the existing send(payload, credentials) contract and registering it — no schema migration needed, since platform is an untyped string column on both SocialAccount and SocialPost.

What would NOT extend cleanly: buildCaption() is a single function with hardcoded if (platform === "x") branches living in lib/review-queue.ts — a file whose primary job is the review-approval workflow, not social publishing. A 6th platform means editing this central conditional rather than adding an isolated module, and the branches already show real per-platform divergence (Twitter gets hashtags and a 280-char clip; Telegram gets neither hashtags nor a length limit; everything else falls to a generic catch-all). The dead lib/social/generate.ts is actually the more scalable design for this specific layer (per-platform PLATFORM_HINTS, no hardcoded conditionals) — reviving and wiring it in, rather than writing a new system, is the natural path forward if it's ever prioritized.

What is structurally Review-only regardless of platform: SocialPost.reviewId is a hard, non-nullable foreign key. Extending social publishing to Tools, Comparisons, or Prompts — regardless of which channels are involved — needs either a nullable/polymorphic reference or parallel foreign keys, a real schema decision, not a code-only change.

Bottom line

The sending layer scales to new channels with near-zero friction. The authoring layer and the content-type coverage do not, and both would need deliberate design work — not a redesign of what exists, but a genuine extension of it.

11

Recommendations

Ordered by how directly each one addresses a Critical or High finding above. No implementation was done — these are documented options for a future sprint.

1

Fix the parse_mode/formatting mismatch

Either switch the Telegram caption template to HTML tags (<b>) to match the existing parse_mode: "HTML", or switch parse_mode to "Markdown"/"MarkdownV2" to match the existing asterisk syntax — either resolves the visible formatting defect with a one-line change.

2

Close the duplicate-send window

Wrap the send + status-update in a single prisma.$transaction, or mark the post as sending before the API call and check that guard on the next cron pass — either removes the crash-window risk.

3

Make the cron-secret check fail closed

An unset CRON_SECRET should reject the request, not silently authorize it.

4

Add a bounded retry with backoff for transient failures

Distinguish rate-limiting (HTTP 429, honor Telegram's retry_after) and network errors from permanent failures (bad credentials, bot blocked) — only the latter should be terminal.

5

Retire or fix the orphaned scripts and stale documentation

check-social-deep.ts, check-pending-posts.ts, fix-pending-posts.ts, and the relevant sections of PROJECT_OVERVIEW.md all describe a system that no longer exists.
