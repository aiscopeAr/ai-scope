Executive Summary

Every P0/P1/P2 item from the brief is implemented and validated against the same 100 real published reviews the Sprint 4 audit scored — not synthetic examples.

The headline diversity engine replaces the single "pose the deeper question" instruction with 8 named angles (breaking, stakes, company-first, number-first, comparison, research, industry, future), picked deterministically per-topic so future drafts stop collapsing onto "هل/كيف" — the exact 94%-repetition finding from Sprint 4. This only affects newly generated headlines; re-scoring the same 100 already-published reviews still shows 88% question-openers, because their titles were written before this change exists. That's expected, not a gap — headline text is fixed at draft time by writeReview(), and this sprint doesn't touch or regenerate existing Review rows.

Everything else — the premium divider/bullet layout, sendPhoto delivery, CTA rotation, hashtag priority, the new 🏢 company template, OG image refinements, and the internal editorial score — applies immediately to every review, including all 100 already-published ones, because these live in the Telegram-composition layer that runs fresh at send/preview time rather than being baked into stored article fields. Re-rendering the real 100-review dataset through the new pipeline: 0 malformed HTML, 0 duplicate headlines, CTA repetition dropped from "always 1 phrase" to a genuine 2–3-way rotation per template, and the 🏢 template correctly claimed 33 posts that previously fell into the generic "general" bucket.

Architecture Decisions

Determinism over randomness

Every rotation (headline style, CTA) is a stable hash, not Math.random()

Headline style is picked by hashing the topic string; CTA is picked by hashing the review's slug. Same input always produces the same output — a retry of the same draft or a repeated admin preview never shows a different result, matching the existing "deterministic, derived from real data" discipline the codebase already uses for template classification and hashtags.

Zero schema changes

Hashtag priority reuses the existing tags[] field — no new Review columns

There's no separate product/company field on Review. Tags in this dataset already follow a real pattern: Latin-script tags are product/company names ("GPT-5.6", "OpenAI"), Arabic-script tags are descriptive technology terms. Splitting on script reuses that existing signal instead of adding a schema field the brief explicitly rules out touching.

Caption-length safety belongs in the provider

sendPhoto's 1024-char cap is enforced client-side, never surfaced to Telegram as a 400

sendPhoto's caption limit (1024) is well under sendMessage's (4096), and the new premium layout with dividers is longer than the old flat paragraph. fitCaption() trims on the last line break within budget before the request goes out — so a too-long caption never becomes a permanent 4xx that the retry classifier would give up on. This is provider-local; lib/social/retry.ts was not touched.

One shared formatter, unchanged contract

buildReviewTelegramMessage() still owns composition — preview and production still call it call-for-call

The only addition is that its result now also exposes the unrendered `parts` object (for the editorial score to read). The `body` string production actually sends is unchanged in shape/derivation — a preview still can never show something different from what gets sent.

Reading time computed once, shown twice

estimateReadingMinutes() is now exported and reused by the OG image

Previously private to telegram-message.ts. The OG image needed the same number for its new reading-time chip — reusing the existing function instead of writing a second, possibly-divergent word-count formula keeps both surfaces in agreement for the same article.

Score is a pure function, wired into exactly one place

scoreTelegramMessage() has no I/O and is called only from the admin preview route

It reads TelegramMessageParts + the already-rendered body and returns a plain object — never touches the database, never called from the provider or the cron route, and its output is never concatenated into the caption text. The "never sent to Telegram" requirement is structural, not a convention someone could accidentally violate from inside renderTelegramMessage() or the provider.

05

Remaining Opportunities

Not blockers — the sprint's own scope boundary (presentation only, no schema/queue/retry changes) is what puts these next in line rather than in this sprint.

P1

Headline diversity only reaches new drafts

The 8-style engine changes what writeReview() produces going forward. The 100 already-published reviews keep their existing titleAr — there's no regeneration step in this sprint's scope (that would mean rewriting published article titles, a bigger and riskier change than a presentation sprint should make unilaterally).

P1

CTA/style hash spread isn't perfectly uniform

djb2-style string hashing gives good but not statistically perfect distribution over a 3-item pool (e.g. company template showed 15/14/4 rather than ~11/11/11 across 33 posts). Good enough to kill the "always identical" failure mode; a larger sample or a different hash could tighten this further if it matters later.

P2

🎯 Prompt/Playbook template still unassigned

Named in the Sprint 4 style guide for the Prompts Library feature, but that feature doesn't post to Telegram yet — nothing to classify into it. Add the category/token check when Prompts Library gains a Telegram path.

P2

Editorial score has no historical trend view

Currently computed fresh per-preview-request with no persistence — an editor sees today's score but can't yet see "channel average over the last 30 days." Would need a small aggregation job, deliberately out of scope for a presentation-only sprint.

P2

2 broken article links from the Sprint 4 audit are still unfixed

Empty-slug reviews reaching the Telegram layer is an upstream editorial/data issue (in approveReview), not something the Telegram presentation layer can fix — flagged again here since it's still live.
