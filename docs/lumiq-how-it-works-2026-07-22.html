How Lumiq actually works, end to end

Not a diagram of the intended design — this is the pipeline as it exists in the codebase today, verified this week by running each stage against the real production database. Six automated stages turn an RSS feed into a published, cached, indexed Arabic article with no human in the loop by default.

1

Fetch news

Reads every enabled RSS/Atom source, keeps only AI-relevant items with enough real content, and queues them as raw material.

Schedule
0 6 * * * — daily, 06:00 UTC
Entry point
app/api/cron/fetch-news/route.ts
Core logic
lib/rss.ts — fetchRssFeed()
Writes to
NewsItem (status: pending), SourceRun (outcome log)
Sources today
20 active feeds, priority-ranked 1–10

  1. Pull every enabled Source, highest priority first

    Each source carries an RSS URL, a priority weight, and a lastSyncedAt timestamp — updated whether or not anything useful was found.

  2. Parse RSS 2.0 or Atom

    Handles both <description>/<content:encoded> (RSS) and <summary>/<content> (Atom) — including Atom's attribute-only <link href="…"/>, which earlier silently dropped every item from Atom feeds until this week's fix.

  3. Drop anything under 100 characters of real content

    A minimum-length gate on the parsed description filters out feeds that are pure link-lists with no article text (a few sources — Hugging Face, TLDR — never clear this and were removed rather than force-fit).

  4. Keyword-filter for AI relevance

    Title + description tested against an AI-topic regex (ai|llm|gpt|claude|gemini|openai|neural|transformer…) before it's allowed into the queue — a general-tech source like TechCrunch or Ars Technica only contributes its AI-relevant subset.

  5. Deduplicate by source URL, cap at 10 new items per source per run

    enqueueNewsItem() checks the URL against existing NewsItem rows before inserting — the same article from the same source can never double-enter the queue.

2

Cluster by topic

GPT-4o-mini groups same-topic items across sources into a single cluster, so five outlets covering the same launch become one article, not five.

Schedule
30 6 * * * — daily, 06:30 UTC
Entry point
app/api/cron/cluster-news/route.ts
Model
gpt-4o-mini, temperature: 0.3, JSON-mode response
Writes to
ReviewQueue (status: pending), links NewsItem rows to it
Minimum size
2 items — a lone item is marked skipped, not force-published solo

Up to 40 pending NewsItems go into one prompt as an indexed headline list. The model returns clusters with a topic phrase, a category guess, and the source indices belonging to each — the same call that assigns the author (see §The 4 authors).

// the exact JSON contract the model returns
{
  "clusters": [
    { "topic": "Gemini 3.5 Flash release", "category": "ai-models", "indices": [0, 3, 7] }
  ]
}
3

Write the article (AI)

The heaviest stage — turns a topic and its source cluster into a full Arabic article, in the voice of one of four fixed author personas, with its own accumulated memory.

Schedule
0 7 * * * — daily, 07:00 UTC, maxDuration: 300s
Entry point
app/api/cron/process-review/route.ts
Core logic
lib/review-openai.ts — writeReview()
Image gen
lib/images.ts → Replicate flux-schnell, generated in this same stage
Writes to
ReviewQueue (status → processed, full draft fields filled)

  1. Resolve the author

    Uses the cluster's category hint (pickAuthor()) unless one of the four personas was already forced upstream.

  2. Retrieve that author's memory

    Two layers: findSimilarReviews() — up to 4 semantically-similar past articles by the same author, via pgvector cosine similarity on a 1536-dim OpenAI embedding — plus an accumulated "voice memory" block (lib/author-memory.ts) built from prior extraction passes. Both get folded into the prompt as context, not just instructions.

  3. Call GPT-4o with the author's fixed system prompt

    Each of the 4 personas (see below) has its own hard-coded voice, opening pattern, and closing-question style — not a shared template with a name swapped in.

  4. Classifier gate: is this actually AI-related?

    The model itself returns isAiRelated; if false, the cluster is marked rejected and never reaches publish — a second filter beyond the keyword regex in stage 1.

  5. Generate the hero image immediately

    Deliberately done here, inside the 300-second budget, rather than in the 60-second publish stage — so image generation failure never blocks the actual publish step later.

4

Publish

Moves a written draft from the queue into the live Review table — the only stage that decides which category a piece lands in and the only one rate-limited per day.

Schedule
0 9 * * * — daily, 09:00 UTC
Entry point
app/api/cron/publish-review/route.ts
Core logic
lib/review-queue.ts — approveReview()
Daily cap
SETTING_KEYS.DAILY_PUBLISH_LIMIT — default 10/day, admin-adjustable
Writes to
Review (published), SyndicationPost, SocialPost

  1. Pick a real Category row by author, not the DB's first row

    Each author maps to specific category slugs (categorySlugCandidatesForAuthor()) — zayd → ai-models/research, lina → companies/ai-policy, tariq → ai-tools, team → tutorials. Before this week's fix, every auto-published article defaulted to whichever category was created first in the database, regardless of topic.

  2. Create the Review row, mark it published

    Slug, title, content, sources (JSON array of the original news items), SEO fields — all copied over from the queue draft as-is.

  3. Fire the best-effort side effects — none of them block publish

    Four independent, individually-caught async calls: embed the new article into pgvector (feeds stage 3's memory retrieval for future articles), extract author-memory signal from it, cross-post to a partner WordPress site if configured, draft social posts for any enabled SocialAccount.

  4. Invalidate the cache immediately

    revalidateNow() on the reviews and categories tags, plus revalidatePath on the homepage and the article's own URL — so the new piece appears in listings within the same request cycle instead of waiting out a cache window.

5

Serve & cache

Where a request actually gets answered from — and the one piece of this system that looked right for months while quietly doing nothing.

⚠

The load-bearing fact about this stack: Next's export const revalidate = N only caches fetch() calls. This codebase reads exclusively through Prisma. Every listing page carrying that config was re-querying Postgres on every request regardless of what the number said — fixed this week by wrapping the actual data-fetching functions in unstable_cache with explicit tags, everywhere it matters.

RouteMechanismWindow
/reviews/[slug]Static (generateStaticParams) + ISR3,600s
/reviews, /category, /tag, /ai-tools, /promptsunstable_cache (tagged)300s + on-publish invalidation
/ai-tools/[slug]unstable_cache — read path only, viewCount write stays uncached300s
/ (homepage)ISR60s

The viewCount increment on a tool page is deliberately kept outside the cached function — caching that call too would mean the counter only ticks once per cache window instead of on every real view.

SEO layer

What makes a published page findable — sitemap, structured data, and the internal link graph that ties everything together.

Discovery surfaces

  • app/sitemap.ts658 URLs — reviews, tools, prompts, comparisons, categories, 54 tag hubs
  • app/robots.tsallows Googlebot/Bingbot; blocks GPTBot/CCBot/Claude-Web
  • app/rss.xml, /news-sitemap.xmlsecondary submission channels

Structured data (JSON-LD)

  • Articlereviews, compare pages
  • SoftwareApplicationtool pages
  • FAQPagereviews and tools with FAQ content
  • CollectionPagetag, category, prompts, ai-tools listings

Internal link graph

Every listing page (/reviews, /category/[slug], /tag/[tag]) now paginates with real <a href> links rather than JS-only click handlers — the single biggest fix to crawlability this month, since 203 of 227 reviews had no link path to them at all before it. Tool pages recommend by matching toolCategory; articles recommend by matching tag or category.

The 4 authors

Not four names for one voice — four fixed system prompts, each with its own opening pattern, evidentiary style, and closing question. Defined in lib/authors.ts.

AuthorCoversVoicePublished

→

Each author also gets a "memory" — up to 4 of their own past articles on similar topics, retrieved by embedding similarity, folded into every new prompt. This is why the same author's coverage develops continuity over time rather than reading like independent one-off pieces.
